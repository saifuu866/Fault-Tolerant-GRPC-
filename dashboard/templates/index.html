Interactive Demonstration Scenarios

Follow these structured walkthroughs to test every resilience mechanism in the distributed framework. Each card explains the expected distributed systems behavior and includes a 1-click preset button to load the test parameters.

Scenario 1

Normal Round-Robin Load Balancing

Tests fair request distribution across all healthy backend replicas with zero failures.

1. Action: Send 6 echo requests with payload "hello".
2. Expected: All 6 succeed. The distribution bars show an exact 2 / 2 / 2 request split across server-1, server-2, and server-3.
3. OS Concept: Round-robin CPU scheduling applied to distributed network processes.
Scenario 2

Server Failure & Transparent Failover

Simulates a sudden node crash while requests are actively in flight.

1. Action: Click Kill on server-1, then send 4 requests.
2. Expected: server-1 immediately turns OFFLINE. All subsequent requests are transparently redirected to server-2 and server-3 with 0 client errors.
3. OS Concept: Fault isolation and graceful degradation.
Scenario 3

Transient Failures & Backoff Retries

Demonstrates handling temporary hiccups (e.g. locks or packet loss) with automatic retry.

1. Action: Send flaky with payload "1" and count 1.
2. Expected: Attempt 1 returns ABORTED. The client pauses (0.4s backoff) and retries on attempt 2, which succeeds. The Retry Attempts card increments.
3. OS Concept: Exponential/linear backoff and transient fault tolerance.
Scenario 4

Permanent Client Errors (Fail-Fast)

Proves that unrecoverable errors are NOT retried, preventing wasted cluster capacity.

1. Action: Send operation boom (or sum with malformed input "abc").
2. Expected: Fails immediately on attempt 1 with INVALID_ARGUMENT. Total attempts = exactly 1 (no retries).
3. OS Concept: Error classification & fail-fast design principle.
Scenario 5

Probationary Server Recovery

Demonstrates the 2-probe health transition before admitting a recovered node back to traffic.

1. Action: Click Revive on a previously killed server and watch its badge.
2. Expected: Status transitions OFFLINE → RECOVERING (probation) → ONLINE. Traffic only resumes once ONLINE.
3. OS Concept: Two-phase commit / health watchdog hysteresis.
Scenario 6

Leader Election & Re-election Failover

Tests coordinator-managed leader election when the current leader crashes.

1. Action: Check Current Leader (e.g. server-1), then click Simulate Leader Failure.
2. Expected: server-1 goes offline. The leader card immediately updates to server-2. Event log records election handover.
3. OS Concept: Distributed mutual exclusion and coordinator election.

Fault-Tolerance Specifications & Formal State Machines

Detailed technical documentation of the health state transitions, error classification rules, and mathematical backoff formulations governing the system.

Server Health Lifecycle (3-State Machine)

Watchdog probe transitions and probation hysteresis

ONLINE Receiving live traffic
→ 1 failed probe (Crash / Timeout) →
OFFLINE Excluded from pool
→ 1 successful probe →
RECOVERING Probation (No traffic)
→ 2nd successful probe → back to ONLINE
Hysteresis Protection: A reviving server enters RECOVERING for 1 probation cycle before rejoining the load balancer. This prevents "flapping" nodes from degrading cluster performance.
Instant Eviction: If a client RPC encounters a connection crash (UNAVAILABLE), the failover manager immediately marks the node OFFLINE without waiting 2s for the next probe.

gRPC Error Classification Matrix

How the client proxy determines whether to retry, failover, or abort

gRPC Status Code Error Category Underlying Cause Coordinator Action Client Strategy
UNAVAILABLE, DEADLINE_EXCEEDED Crash / Network Server process down, port unreachable, or unresponsive. Server set to OFFLINE immediately. Failover to a different server; retry up to 3x.
ABORTED, RESOURCE_EXHAUSTED, INTERNAL Transient Error Temporary lock contention, memory spike, or simulated glitch. Server remains ONLINE. Wait backoff delay (0.4s × attempt); retry.
INVALID_ARGUMENT, NOT_FOUND, UNIMPLEMENTED Permanent Error Bad input data, missing method, or validation failure. No server state change. Fail-fast: abort immediately with 0 retries.
